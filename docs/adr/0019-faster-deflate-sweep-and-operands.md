# ADR 0019: Deflate の探索、密な格子の掃き出し、演算子の数を、バイト列を変えずに速くする

ステータス: 採択→交点の積の検査は[ADR 0020](0020-carried-crossings-for-every-i64.md)

## 文脈

v0.1.0-rc5 の後、高速化できるところを高速化してほしいという依頼があった（2026-11-07）。
手元の Mac（Apple M1 Max）で、`tests/fixtures/golem/kanikosen.pdf`（129 ページ）を `--jobs 1` で描き、`/usr/bin/time -l` の命令数を見た。
測った時点で、機械の負荷平均は 70 を超えていた。
実時間は当てにならないので、命令数、サイクル数、ユーザー時間で比べた。

| 形式と解像度 | 命令数 |
|---|---|
| PPM、72 dpi | 31.6 億 |
| PPM、150 dpi | 44.5 億 |
| PNG、150 dpi | 114.0 億 |
| PPM、300 dpi | 76.3 億 |

既定の 150 dpi の PNG では、命令の約 6 割が PNG の書き出しだった。
解像度に比例する部分（描画）は、ブラウザのプレイグラウンドが 300 dpi で 1 ページずつ描く wasm（[ADR 0018](0018-wasm-module-for-the-browser.md)）で効く。

この三つ（PNG の書き出し、描画、解像度によらない部分）を、別々の試作で調べた。
どの試作も、出力が main（`f60c40c`）とバイト単位で同じことを確かめながら進めた。

### PNG の書き出し

150 dpi の PNG の 114 億命令のうち、Deflate が約 52 億、Adler-32 が約 2.9 億、残り（フィルタ、CRC、領域）が約 14 億だった。
129 ページのフィルタ後のデータは 3 億 1,400 万バイトある。
探索した位置は 935 万、一致は 844 万（平均 37 バイト）、リテラルは 90 万だった。
連鎖の候補は 3,800 万で、そのうち 2,400 万は、最長の一致の次のバイトの比較で外れた。
連続の候補をまとめる処理（[ADR 0015](0015-faster-png-render-and-decoding.md) の `run_group`）は 445 万回だった。
探索が時間の大半を占め、多くの位置が同じバイトの連続の中にある。

試作では、次の変更で命令数が 114.7 億から 107.4 億（6.4% 減）、サイクル数が 36.6 億から約 34.3 億（約 6% 減）になった。

| 段階 | 命令数 | サイクル数 |
|---|---|---|
| main | 114.7 億 | 36.6 億 |
| 連続の比較を語で行い、今の位置の連続とハッシュを使い回す | 110.9 億 | 33.2 億 |
| フィルタの費用を u32 で足す | 108.2 億 | |
| Adler-32 の列を u16 で足す | 107.4 億 | 約 34.3 億 |

試したが入れないものもある。

- Paeth のフィルタを 8 ビットの演算（`abs_diff` と飽和の演算）で書き、16 個ずつの演算にさせること。全数のテストは通ったが、命令数は 110.9 億から 116.0 億、サイクル数は 33.2 億から 36.5 億に増えた。

### 描画

300 dpi で密な格子（[ADR 0014](0014-thread-workspaces-and-faster-check-and-fill.md)）を数えると、格子の場所の 43% が、行の最初に足された場所より左か、最後に足された場所より右にあった。
今は、その場所も含めて行のすべての場所を足しながら掃いている。
また、交点の座標（[src/raster.rs:217](https://github.com/tett23/shem/blob/f60c40cdc67871e17256a09437fd337ada078340/src/raster.rs#L217) の `interpolate`）は、交点ごとに i64 で割っている。
プロファイルでは、この割り算に描画の 1 割近いサンプルが落ちていた。

試作では、kanikosen を描くだけ（ファイルを書かない）の時間が、300 dpi で約 9% 減り（1.32 秒から 1.20 秒、別の系列で 1.25 秒から 1.14 秒）、150 dpi で約 2% 減った（ユーザー時間の中央値。main と交互に走らせた）。
途中から命令数のカウンターが読めなくなったので、この節はユーザー時間で比べた。

試したが入れないものもある。

- グリフの覆いのページごとのキャッシュ。鍵を、フォント、CID、行列の a、b、c、d、e と f の画素未満の部分とした。整数の画素の平行移動は二度の丸めと交換でき、バイト列は同じだった。しかし 6 万個のグリフで、一度も当たらなかった。Golem の文字の行列は送りを Q32.32 で丸めながら足すので、画素未満の部分が一つのページの中で繰り返さない。ユーザー時間は 10〜15% 増えた。鍵を粗くすると、バイト列の同一を示せない。

### 解像度によらない部分

72 dpi の PPM の 32.3 億命令の内訳を、段階ごとに止めた版との差で測った。

| 段階 | 命令数 |
|---|---|
| 起動と `Document::parse` | 1,800 万 |
| `pages_with`（ページの木と、4.6 MB の内容の展開） | 8,200 万 |
| 内容の字句と演算子の解析 | 3 億 800 万 |
| 検査 | 約 6 億 4,000 万 |
| 描画 | 約 21 億（1 dpi でも約 9 億 7,000 万） |
| 129 個の PPM の書き出し | 3 億 8,000 万（約 3 億はカーネルでの作成、書き込み、名前の変更） |

解像度によらない部分の大半は、読み込みではなく、グリフごとのパスの組み立てと塗りの固定の費用だった。
試作では、次の変更で命令数が 32.3 億から 31.0 億（4.2% 減）、サイクル数が 11.5 億から 10.2 億（11% 減）になった（5 回の中央値）。
`--pages 1`（文書を開く費用）では、2.28 億から 2.19 億になった。

- 演算子の数を `Object` に包まずに置く。
- `Error` の中身を `Box` に入れ、`Result<Fixed>` を 80 バイトから 16 バイトにする。
- PPM のヘッダーを一度に書く。

### 三つを合わせた試作

三つの試作を一つのブランチにまとめると、ぶつからずにまとまり、`cargo test` が通った。
fixture の五つの PDF を、72 dpi と 97 dpi の PPM、150 dpi の PNG、300 dpi の PPM と PNG で描いた 695 個のファイル、標準エラー、終了コードは、どれも main と同じだった。
kanikosen の `--jobs 1` のユーザー時間（3 回、秒）は次のとおりだった。

| 形式と解像度 | main | 合わせた試作 |
|---|---|---|
| PPM、72 dpi | 0.36、0.37、0.37 | 0.37、0.36、0.37 |
| PNG、150 dpi | 1.53、1.52、1.52 | 1.40、1.39、1.40 |
| PPM、300 dpi | 1.09、1.09、1.10 | 0.99、0.99、0.96 |

72 dpi の PPM で差が見えないのは、ファイルの書き出しと負荷によるばらつきに埋もれたためと考えられる。
この測定は負荷の高い機械で行ったので、記録には、「測定と文書」の節のとおり測りなおしたものを残す。

## 実装すること

### 原則

- どの変更も、画素、PNG と PPM のバイト列、報告するエラーを変えない。ゴールデンと kanikosen のバイト列の一覧（[ADR 0013](0013-fewer-allocations-for-musl-threads.md)）を、作り直さずに通すことを条件とする。
- 依存は増やさない。`unsafe` も、特定のアーキテクチャの組み込み関数も使わない。wasm32-unknown-unknown でも同じコードで動く。

### PNG の書き出し

- **連続の比較**：`run_group` に入るかの判定で、候補 c の c − 1 から c + 2 の 4 バイトを、一つの u32 として `[b; 4]` と比べる。判定の条件は同じである。
- **直前の候補**：候補が今の位置 i の直前（i − 1）のとき、候補からの連続の長さ A は、i の連続の長さ r に 1 を足したものである（r < `max` のとき）。連続を数えなおさない。
- **今の位置の連続とハッシュの使い回し**：探索で数えた i の連続の長さと i のハッシュを、探索の後の位置の追加で使う。r < `max` なら連続の長さはちょうど r である。r = `max` なら、`max` より先の 2 バイトまでを読む。リテラルを足すときも、同じハッシュを使う（今は二度計算している）。
- **位置の追加**：連続の外の位置は、`windows(3)` の 3 バイトからハッシュを求めて足す。転がすハッシュは使わない。`head` と `prev` を固定の長さの配列（`Box<[u32; N]>`）にし、マスクした添字の境界の検査を省かせる。書く項目と順は同じである。
- **長さの数えの終わり**：`match_length`、`run_length`、`run_back` で、8 バイトに満たない残りを、等しいとわかっているバイトに重ねた 8 バイトの語一つで比べる。最初に違うバイトの位置は同じである。
- **最長の一致の次のバイト**：候補を外す比較（[ADR 0015](0015-faster-png-render-and-decoding.md) の「候補の打ち切り」）に使う i + `best_len` のバイトを、`best_len` が変わるときだけ読みなおす。
- **フィルタの費用**：2^24 バイト以下の行では、費用の和（2^31 以下）を u32 で足す。長い行は今と同じく u64 で足す。
- **Adler-32**：16 本の列の和を、256 バイト以下の部分ごとに u16 で足し（255 · 256 は u16 に収まる）、部分の終わりに u32 の列に `lb += m · la + pb; la += pa` で畳む。代数的に同じ和で、5552 バイトの塊と剰余を取る位置は変えない。

### 描画

- **交点の商と余りの持ち越し**：線分が横切る行（と、行の中の列）の座標は、一定の間隔で並ぶ（`crossings`）。積が i64 に収まるときは、最初の交点の積だけを割り、次からは、前の商と余りに、間隔の積の商と余りを足して、一度だけ繰り上げる。ユークリッドの商と余りは足し算で保たれるので、`div_round_i64` と同じ商と余りになり、丸め（最近接、同じなら偶数）も同じである。積が収まるかは、線分ごとに `db · d` で一度だけ確かめる（どの交点も |at − a0| < d）。収まらなければ、今と同じく交点ごとに `interpolate` を使う。
- **行ごとの画素の受け渡し**：塗りの掃き出しは、行の連続する画素の不透明度を、一つの領域に書いて渡す（`visit_rows`）。`Canvas::fill` は、その範囲の画像を `chunks_exact_mut(3)` で塗る。不透明度 0 の画素は、合成の式で値が変わらないので、範囲の中にあってよい。`visit_coverage` は `visit_rows` の上に作り、今と同じ画素を同じ順に出す。
- **触れた範囲の掃き出し**：密な格子の行ごとに、最初と最後に足された場所を記録する。掃き出しはその範囲だけを行う。範囲より左の場所は、覆いも面積も 0 なので画素を出さない。範囲より右の場所は、行の覆いの累積が変わらないので、格子の右の列と同じ不透明度になる。その不透明度が 0 より大きいとき（右の端で切ったパス）だけ、範囲の右から画像の右の端までを一つの範囲として渡す。
- **格子の 0 の保ち方**：掃いた範囲の場所を掃き出しの後で 0 に戻し、格子を塗りの間で 0 に保つ。格子は伸びるだけにし、塗りごとに全体を 0 で埋めない。[ADR 0015](0015-faster-png-render-and-decoding.md) で試して入れなかった「読むときに 0 にする」形とは違う。
- **黒の塗り**：色が黒のときは、合成の式 `(c · a + p · (255 − a) + 127) / 255` の c · a が 0 なので、`(p · (255 − a) + 127) / 255` で計算する。

### 解像度によらない部分

- **演算子の数**：内容の字句の整数と実数を、`Object` に包まずに、オペランドのスタックに数として置く（`Operand::Int`、`Operand::Real`）。値（同じ i64 からの `Fixed::from_int`）とオペランドの検査（`Tr` は整数を求める）は同じである。参照を読まない `object_from` は、数でエラーを返さないので、エラーも変わらない。
- **`Error` の大きさ**：`Error` の中身（ページ、オブジェクト、位置、文）を `Box` に入れ、`page()`、`object()`、`offset()`、`message()` で読む。`Display` と `at_page`、`at_object`、`at_offset` の意味（内側の場所が勝つ）は変えない。クレートのライブラリは v0.x の間、版を上げずに変わりうる（README）。
- **PPM のヘッダー**：ヘッダーを、`File` への `write!` ではなく、同じ文字列を一度の `write_all` で書く。

### 測定と文書

- 変更の前と後を、手元の VM（または負荷の低い機械）と、ワークフロー Benchmark（ubuntu-24.04）で、72 dpi の PPM、150 dpi の PNG、300 dpi の PPM について測り、`docs/benchmarks/` に記録として残す。
- wasm での効果は、300 dpi で kanikosen の数ページを描く時間を、Deno で測って記録に添える。
- 仕様（決定性の節とライブラリの節）を、この ADR に合わせて書き直す。

## 実装しないこと

- PNG のバイト列を変える高速化。[ADR 0016](0016-options-past-byte-identical-speed.md) で却下した。
- グリフの覆いのキャッシュ。上の試作のとおり、Golem の PDF では当たらず、遅くなる。
- Paeth のフィルタの 8 ビットの演算。遅くなった。
- 5 種類のフィルタの費用を一回の走査で求めること。白い行で費用 0 の打ち切りが効かなくなり、種類ごとのループはすでに 16 個ずつの演算になっている。
- 連続の始まりの位置の表を持ち、`run_back` を省くこと。連続は位置の追加の途中で分かれることがあり、表を正しく保つのが難しい。
- 字句で読んだ数字を `Fixed::parse` に渡して読みなおしを省くこと。数 1 個あたり約 30 命令の見込みで、ほかの変更より小さい。
- 格子の場所を i32 にすること。異常な入力で桁あふれし、バイト列が変わりうる。

## テスト設計

### 出力が変わらないこと

- 既存のゴールデン、kanikosen の 516 個のファイルのバイト列、fixture の演算子の列を、作り直さずに通す。
- 実装の後、fixture の五つの PDF を 72、97、150、300 dpi の PPM と、150、300 dpi の PNG で描き、main の出力、標準エラー、終了コードと同じことを確かめる（自動のテストにはせず、プルリクエストに結果を書く）。

### PNG の書き出し

- [ADR 0015](0015-faster-png-render-and-decoding.md) の参照の実装（`src/png/reference.rs`）との比較を、そのまま通す。
- 連続の多いデータを足す。長さ 1〜300 の同じバイトの連続を、間に 1〜3 バイトを挟んで並べ、連続の長さが `max`（258）の前後、ウィンドウの 32 KiB の前後になる 300 個のデータで、zlib のストリームが参照と同じである。直前の候補で連続が `max` ちょうどと `max` + 1、+ 2 になる場合を含む。
- 長さの数えの終わり：長さ 0〜40 の二つのバイト列のすべての組の、最初に違う位置をずらした 2 万組で、`match_length`、`run_length`、`run_back` が、1 バイトずつ数えるものと同じ値を返す。
- フィルタの費用：長さ 0〜5,000 のランダムな行と、255 だけの行で、u32 の和が u64 の和と同じである。2^24 バイトの境目は、費用の上限の式で確かめる。
- Adler-32：長さ 0〜2 万のデータ（255 だけのもの、長さが 255、256、257、5551、5552、5553 のものを含む）300 個で、参照と同じ値になる。

### 描画

- 交点：20 万組の線分（i32 の端の値、積が i64 に収まらないものを含む）で、`interpolations` が、交点ごとの `interpolate` と同じ座標を返す。間隔の積が負の場合と、交点が一つだけの場合を含む。
- 触れた範囲の掃き出し：小さな画像と大きな画像に 40 個ずつのランダムなパス（画像の右の端と左の端で切れるもの、列 −1 に覆いを足すものを含む）を、二つの塗りの規則で重ねて塗り、`Canvas::fill` と `coverage` を `Canvas::paint` した画像が同じである（[ADR 0015](0015-faster-png-render-and-decoding.md) のテストを、端で切れるパスで厚くする）。
- 格子の 0 の保ち方：大きさの違うパスを 200 個続けて同じ `Scratch` で塗った後、格子のすべての場所が 0 である。続けて塗った画像が、塗りごとに新しい `Scratch` で塗った画像と同じである。
- 黒の塗り：すべての不透明度と画素の値で、`paint_black` が `composite(0, a, p)` と同じである。

### 解像度によらない部分

- 演算子の数：既存の内容の解析のテストと、fixture の演算子の列を通す。整数、実数、境目の値（i64 の端、範囲の外の整数）を並べた内容で、オペランドの値と、`Tr` に実数を渡したときのエラーが今と同じである。
- `Error` の大きさ：`size_of::<Result<Fixed>>()` が 16 バイト以下である。`at_page`、`at_object`、`at_offset` を重ねたときの `Display` が今と同じである。
- PPM：既存の PPM のバイト列のテストを通す。

### 速さ

- 自動のテストにはしない。上の「測定と文書」のとおり記録する。

## トレードオフ

- 合わせた効果は、150 dpi の PNG と 300 dpi の PPM で約 1 割である。[ADR 0015](0015-faster-png-render-and-decoding.md) の 2 倍前後に比べて小さく、そのかわり証明に頼る部分（連続の長さの使い回し、商と余りの持ち越し、触れた範囲の外の画素）が増える。どれも参照との比較のテストで確かめ続ける必要がある。
- 格子を 0 に保つ形は、塗りの途中でパニックすると 0 でない場所が残る。CLI はパニックで終わり、wasm はトラップの後にインスタンスを読みなおす（[ADR 0018](0018-wasm-module-for-the-browser.md)）ので、残った格子が後の塗りに使われることはない。ライブラリでパニックを捕まえて同じ `Workspace` を使い続けると、画像が変わりうる。
- `Error` のフィールドを読む形が、フィールドから関数に変わる。クレートのライブラリを使う側には、互換でない変更である。
- 試作の測定は、負荷平均が 70 を超える機械で行った。数字は記録として残す前に測りなおす。
