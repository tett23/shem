# ADR 0015: PNG の書き出し、描画、Flate の展開を、バイト列を変えずに速くする

ステータス: 採択

## 文脈

[ADR 0014](0014-thread-workspaces-and-faster-check-and-fill.md) の後も、限界まで速くしたいという依頼があった（2026-11-05）。

手元の Mac（Apple M1 Max）で、`tests/fixtures/golem/kanikosen.pdf`（129 ページ）を描くと、PNG の書き出しが時間の大半を占めていた。
既定の形式は PNG である。

| 形式と解像度 | `--jobs 1` | `--jobs 10` |
|---|---|---|
| PPM、72 dpi | 0.43 秒 | 0.09 秒 |
| PNG、72 dpi | 1.49 秒 | 0.23 秒 |
| PPM、150 dpi | 0.63 秒 | 0.18 秒 |
| PNG、150 dpi | 4.90 秒 | 0.65 秒 |

8 CPU の colima の VM（aarch64 の Linux）で `perf record` を取ると、次のことがわかった。

- 150 dpi の PNG では、Deflate（[src/png.rs:162](https://github.com/tett23/shem/blob/a8bbd4a00660f514128f74b45578158039176566/src/png.rs#L162)）が約 40%、行のフィルタの選択と行の組み立て（[src/png.rs:257](https://github.com/tett23/shem/blob/a8bbd4a00660f514128f74b45578158039176566/src/png.rs#L257)、[src/png.rs:298](https://github.com/tett23/shem/blob/a8bbd4a00660f514128f74b45578158039176566/src/png.rs#L298)）が約 43% だった。フィルタは、5 種類の費用をバイトごとにクロージャで求め、選んだ行を行ごとの `Vec` に作ってからつないでいた。Deflate は、固定の Huffman の符号をビットごとに反転して書き、長さと距離の符号を表から線形に探していた。
- 72 dpi の PPM では、座標の変換（[src/render.rs:60](https://github.com/tett23/shem/blob/a8bbd4a00660f514128f74b45578158039176566/src/render.rs#L60)）、塗り（[src/raster.rs:336](https://github.com/tett23/shem/blob/a8bbd4a00660f514128f74b45578158039176566/src/raster.rs#L336)）、曲線の平坦化（[src/raster.rs:158](https://github.com/tett23/shem/blob/a8bbd4a00660f514128f74b45578158039176566/src/raster.rs#L158)）が上位だった。検査の段階でも、グリフのすべての点を、桁あふれを確かめながら写していた。
- 並列にならない部分として、全ページの内容の Flate の展開に約 17 ミリ秒、最初のページで読むフォント（675 KB の CFF）に約 9 ミリ秒かかっていた。Huffman の符号は 1 ビットずつ読んでいた（[src/flate.rs:150](https://github.com/tett23/shem/blob/a8bbd4a00660f514128f74b45578158039176566/src/flate.rs#L150)）。8 スレッドでは、PPM の全体が約 120 ミリ秒なので、この部分の割合が大きい。

### 試作での確かめ

それぞれを直す試作を作り、出力が v0.1.0-rc3 とバイト単位で同じことを確かめながら測った。手元の Mac で、kanikosen の 150 dpi の PNG を 1 スレッドで描いた時間は次のように変わった（1 回ずつ、秒）。

| 段階 | 時間 |
|---|---|
| main（[ADR 0014](0014-thread-workspaces-and-faster-check-and-fill.md) の後） | 4.90 |
| フィルタを種類の順に試し、費用 0 で打ち切る。固定の符号を表にする | 2.83 |
| 一致の長さを数える前に、最長の一致の次のバイトで候補を外す | 2.44 |
| フィルタをスライスのループにする | 2.09 |
| 最初の画素とそれ以降を別のループにする | 1.73 |
| 同じバイトの連続の中の候補を、まとめて閉じた式で処理する | 1.38 |

Deflate の候補を数えると、試した候補の 79% が同じバイトの連続の中にあった（20 ページで、1 回の圧縮あたり 2,962 万回のうち 2,338 万回）。この段階の後、20 ページの PNG の書き出しは、テストの中で次のように変わった（ミリ秒）。

| 段階 | Deflate | PNG の書き出し |
|---|---|---|
| 連続の候補をまとめた後 | 128 | 152 |
| 連続の位置を、連続の長さを 8 バイトずつ数えてまとめて連鎖に足す | 108 | 132 |
| Adler-32 を 16 本の列で計算する | 93 | 116 |
| CRC-32 を 8 バイトずつ計算する | 93 | 110 |
| 一致の符号を一度に書く | | 105 |
| 連続の内側の位置の連鎖を書かない | | 101 |

部品を一時的に止めた版との時間の差から、この後の 20 ページの PNG の書き出し（約 100 ミリ秒）の内訳は、一致の後の位置の追加が約 10 ミリ秒、最初の候補より後の探索が約 35 ミリ秒、残り（最初の候補の比較、符号の書き出し、フィルタ、検査値）が約 55 ミリ秒だった。

字句と演算子の解析は、検査と描画のそれぞれで約 21 ミリ秒（129 ページ）かかり、検査の時間の大半だった。字句の語の終わりと数の形を 1 回の走査で調べ、整数を直接読むと、17.5 ミリ秒になった。

検査では、十進の数と、グリフの寸法を 1000 で割るところも目立った。小数部が 9 桁以下の十進の数を u64 で読み、整数で割る \`checked_div\` を i64 で行うと、検査は 36.8 ミリ秒から 33.0 ミリ秒になった（9 回の中央値）。

PPM の描画と検査は、テストの中で 7 回ずつ繰り返した中央値で測った（ミリ秒）。

| 段階 | 検査 | 描画 |
|---|---|---|
| 変更の前 | 71 | 292 |
| `interpolate` を i64 で計算する | 71 | 283 |
| 密な格子を直接掃く | 69 | 266 |
| 収まる点を検査なしで写す | 72 | 254 |
| 平坦化を再帰にする | 69 | 229 |
| 上限の判定に使う広がりをキャッシュに入れる | 62 | 221 |
| 画素を掃きながら重ねる | 56 | 215 |

全ページの内容の展開は、表で引く復号と 4 バイトの先読みで 17 ミリ秒から 9 ミリ秒になった。最初のフォントの展開は、表のビット数を 9 から 11 にして 7 ミリ秒から 5 ミリ秒になった。

試したが効かなかったものもある。

- Deflate で、同じハッシュが続く位置を、ハッシュを 1 バイトずつ転がして見つけ、まとめて連鎖に足すこと。時間は変わらなかった。連続の長さを 8 バイトずつ数える形にしてから効いたので、その形で入れる。
- Flate のビットの読み手を、64 ビットの貯めを持つ形にすること。速くならなかったので入れない。
- PNG のフィルタの選択で、勝ちそうな種類を先に数え、ほかの種類を途中で打ち切ること。速くならなかったので入れない。
- 密な格子の掃き出しで、塗りの規則ごとの関数を `dyn` で渡すこと。遅くなったので入れない。
- Adler-32 を、16 バイトの塊ごとに和と重みつきの和で計算すること。遅くなった（18 ミリ秒から 27 ミリ秒）ので、列ごとの和の形にした。

## 実装すること

### 原則

- どの変更も、画素、PNG と PPM のバイト列、報告するエラーを変えない。ゴールデンと kanikosen のバイト列の一覧（[ADR 0013](0013-fewer-allocations-for-musl-threads.md)）を、作り直さずに通すことを条件とする。
- 依存は増やさない。`unsafe` も使わない。

### PNG の書き出し

- **フィルタの選択**：5 種類を番号の順に試し、費用（フィルタ後のバイトを符号つきとみなした絶対値の和）が 0 の種類が出たら打ち切る。同じ費用なら番号の小さいものが勝つので、後の種類は選ばれない。
- **フィルタの計算**：種類ごとに、最初の画素（左の画素がない）と残りを、スライスの `zip` の別々のループで計算する。最初の行（上の行がない）も種類ごとに分ける。費用の和と選んだ行の書き込みは、同じ形のループで行う。
- **行の組み立て**：フィルタ後の行を、確保した一つの領域に、種類のバイトと一緒に直接書く。
- **固定の符号**：固定の Huffman の符号を、反転した形で 288 個の表にする。長さと距離の符号は、zlib と同じく表で引く（距離は 256 以下と、それより上の 7 ビット目より上で引く）。ビットは 32 ビットたまったら 4 バイトまとめて書く。
- **ハッシュの連鎖**：連鎖の位置を u32 で持つ。データは 4 GiB より短い（1 ページは最大 2^28 画素、[ADR 0007](0007-png-output-resolution-and-cli.md)）。一致の後に位置を足すときは、直前のハッシュを 5 ビットずらして新しいバイトを足す（マスクで出ていくバイトが落ちるので、値は同じ）。
- **候補の打ち切り**：候補の、今の最長の一致の長さの位置のバイトが、今の位置のものと違えば、その候補はそれより長くならないので、長さを数えない。候補を試した回数（128 の上限）には数える。
- **連続の中の候補**：候補 c が同じバイト b の連続の中にあり（`b b b` で始まり、c − 1 も b）、c − 1、c − 2、… も同じ連続にあるとき、それらは連鎖で連番に並ぶ（どの位置も直前の位置に連鎖されている）。候補から連続の終わりまでの長さを A、今の位置の b の連続の長さを R とすると、一致の長さは、A < R なら A、A > R なら R、A = R なら R 以上で、どれも `max` まで。候補をたどると A は 1 ずつ増えるので、長さは A = R まで増え、その後は R に留まる。長い一致だけが勝つので、連続の中で勝つのは、最も長い長さを最初に出す候補である。A = R の候補だけは一致の長さを数え、ほかは式で決める。試した回数（128 の上限）と窓の大きさの範囲で、連続の候補をまとめて処理し、試した回数を足す。今の位置の直前の候補で、今の位置の連続が `max` 以上なら、答えは距離 1、長さ `max` である。
- **連続の位置の連鎖**：一致の後に位置を連鎖に足すとき、`b b b` で始まる位置は、連続の長さを 8 バイトずつ数えてまとめる。まとまりの最初の位置は今のハッシュの表の値に連鎖し、表にはまとまりの最後の位置を入れる。まとまりの内側の位置の連鎖（直前の位置）は書かない。探索は、連続の中の候補をまとめて式で処理するので、内側の位置の連鎖を読むのは、試した回数か窓で探索が終わるときだけである。そのとき読む場所に 32 KiB 前の古い値が残っていても、その値は窓の外を指すので、探索はそこで終わる。
- **一致の符号**：長さの符号、長さの追加ビット、距離の符号、距離の追加ビット（合わせて 31 ビット以下）を、一度に書く。
- **CRC と zlib**：チャンクの種類とデータを写してつながずに、CRC を続けて計算する。CRC は 8 個の表で 8 バイトずつ引く（slicing-by-8）。zlib のストリームも、つながずに一つの `Vec` に書く。
- **Adler-32**：5552 バイトの塊ごとに、16 本の列でバイトの和 A_l と、塊ごとの A_l の累積 B_l を求め、a に Σ A_l を、b に n a + Σ (16 B_l − l A_l) を足す。1 バイトずつ足した和と同じで、剰余を取る位置も変えない。Flate の展開の検査にも使う。

### 描画

- **検査での点の変換**：グリフのアウトラインの x と y の絶対値の最大（広がり）と行列から、`|a x + c y + e|` の上限を整数で求める。二度の丸め（2^-32 と 1/256 画素）でそれぞれ 1 単位まで増えても 2^31 より小さいと示せれば、検査ではどの点も写さない。示せなければ、今と同じく一つずつ写す（`fits_in_device`）。
- **描画での点の変換**：上限で収まると示せたグリフの点は、同じ和と同じ二度の丸めで、桁あふれの検査なしで写す（`to_device_fitting`）。
- **広がりのキャッシュ**：広がりは、グリフのアウトラインと一緒に、フォントのキャッシュ（[ADR 0011](0011-speed-up-without-changing-bytes.md)）に入れる。
- **交点**：`interpolate` の積が i64 に収まるときは、i64 で割って丸める。商は i128 の場合と同じである。
- **密な格子の掃き出し**：[ADR 0014](0014-thread-workspaces-and-faster-check-and-fill.md) の密な格子は、行ごとに左からすべての場所を足しながら画素を出す。値が 0 の場所は、それを含む区間の画素と同じ画素を出す。
- **塗り**：画素を `Vec` に集めずに、掃きながら画像に重ねる（`Canvas::fill`、`raster::visit_coverage`）。どの画素も一つの塗りで一度だけ出るので、結果は同じである。
- **平坦化**：曲線の分割を、固定の長さの配列のスタックではなく再帰で行う。分割の順（前半が先）は変えない。最初の点の後は、部分パスを確かめずに点を足す。
- **グリフの行列**：フォントの `glyph_matrix` は、フォントを読むときに一度だけ求め、結果（エラーも）をそのまま返す。行列の積は、どちらかが単位行列なら計算せずにもう一方を返す（積は正確にその行列になる）。
- **字句**：バイトの種類（通常の文字、空白、区切り）を表で引く。通常の文字の語は、1 回の走査で終わりを探しながら、数の形（符号のあとに数字と高々一つの点、数字が一つ以上）かを調べる。整数は、文字列に直さずに読み、範囲の外なら今と同じエラーにする。
- **不透明な画素**：不透明度 255 で重ねる画素は、合成の式が色そのものになるので、色を書く。
- **数の読みと割り算**：小数部が 9 桁以下の十進の数は、D · 2^32 が u64 に収まるので、u64 で割って丸める。`Fixed::checked_div` は、割る数が正の整数 k なら、(a · 2^32) / (k · 2^32) が a / k なので、i64 で割って丸める。どちらも値は今と同じである。交点の i64 の割り算は、割る数が負なら両方の符号を反転し、反転があふれるときは i128 で割る。

### Flate の展開と文書の読み込み

- **Huffman の復号**：先の 11 ビットを覗き、表で符号と長さを引く。符号が 11 ビットより長いとき、データの残りが足りないとき、表にない符号のときは、今の 1 ビットずつの復号に任せる。結果もエラーも、エラーの出る位置も同じである。
- **ビットの読み**：データの終わりから 4 バイト以上離れていれば、4 バイトをまとめて読む。必要なビットがあれば、数ビットをまとめて読む。足りなければ、今と同じく 1 ビットずつ読む。
- **一致の写し**：距離が長さ以上なら、重ならないので、まとめて写す。重なるときは今と同じく 1 バイトずつ写す。
- **検査の演算子の使い回し**：`Session::from_pages(doc, pages, dpi)` を加える。`Session` の外で読んだページ（`Document::pages_with`）を借りるので、検査で解析した演算子は、ページの内容を `Session` と同じ寿命で借りられる。検査が通ったページの演算子をページごとに持ち、そのページの描画は、内容を解析しなおさずにそれを使う（使ったら手放す）。検査をしていないページ、検査が失敗したページは、今と同じく描画で解析する。`shem render` はこれを使う。`Session::new` は今と同じく演算子を持たない。手元の Mac で、72 dpi の PPM の `--jobs 1` は 0.28 秒から 0.26〜0.27 秒になった。
- **ページの並列の展開**：`Document::pages_with(jobs)` を加える。ページの木は今と同じく一つのスレッドでたどり、ページごとの内容の展開を `parallel::run` で並列に行う。返すエラーは番号の最も小さいページのもので、一つのスレッドと同じである。`Session::with_jobs(doc, dpi, jobs)` はこれを使い、`shem render` は `--jobs` を渡す。`Document::pages` と `Session::new` は、一つのスレッドの `pages_with` と `with_jobs` である。

### 測定と文書

- `scripts/ci/benchmark.sh` に `DPI` と `FORMAT`（既定は 72 と ppm）を、ワークフロー Benchmark に `dpi` と `format` の入力を足す。ワークフローは、計算機のコアあたりのスレッドの数もログに出す。
- 変更の前と後を、手元の 8 CPU の VM と、ワークフロー Benchmark（ubuntu-24.04、4 vCPU）で、72 dpi の PPM と 150 dpi の PNG について測り、`docs/benchmarks/` に記録として残す。
- 仕様（ライブラリの節と決定性の節）を、この ADR に合わせて書き直す。

## 実装しないこと

- PNG のバイト列を変える高速化（一致の探索の上限を減らす、遅延一致をやめる、動的な Huffman の符号にするなど）。PNG のバイト列は版が違えば変わってよい（[ADR 0007](0007-png-output-resolution-and-cli.md)）が、ゴールデンを作り直すことになり、この ADR の原則（バイト列を変えない）に反する。必要なら別の ADR で決める。
- 一つのページの中の並列化（行の帯ごとの Deflate など）。Deflate を帯に分けると、PNG のバイト列が変わる。
- グリフの覆いのキャッシュ（同じグリフを同じ小数部の位置に描くときの使い回し）。二度の丸めで最近接の偶数に丸めるので、平行移動と丸めが交換できない場合があり、一致を示すのが難しい。
- 検査と描画の一度の解釈へのまとめ。すべてのページを検査してからファイルを書く約束（[ADR 0002](0002-pdf-subset-and-out-of-scope-input.md)）を保つには、描いた画像をすべてメモリに持つ必要がある。
- 最初のフォントの読み込みを並列にすること。一つのフォントの展開は一つのスレッドで行う。

## テスト設計

### 出力が変わらないこと

- 既存のゴールデン、kanikosen の 516 個のファイルのバイト列、fixture の演算子の列を、作り直さずに通す。

### PNG の書き出し

- 書き換える前の PNG の書き出しを、テストの中に参照の実装として残す（`src/png/reference.rs`）。
- 固定の種の 120 枚の画像（大きさは 1〜90 × 1〜70、白地に点、階調、雑音、灰色の箱）と、72 dpi の A5 の大きさ（窓の 32 KiB より大きい）の画像で、PNG のバイト列が参照と同じである。
- 2,000 行（ランダム、0 と 255 と 254 だけ、白だけ。上の行が同じものを含む）で、選ぶフィルタと行が参照と同じである。上の行がない場合も確かめる。
- 60 個のデータ（連続、短い距離と長い距離の繰り返し、雑音。12 万バイトまでのものを含む）で、zlib のストリームが参照と同じである。
- フィルタ後の行に似た 200 個のデータ（0 の連続に、長さ 1〜4、127〜129、257〜259 のバイトの並びを置いた行を、前の行を少し変えながら重ねたもの。バイトの種類を 1、2、3、255 と変える）で、zlib のストリームが参照と同じである。一致の長さ（3 と 258）と、試す回数（128）の境目の前後を含む。
- 窓の 32 KiB の前後と、それより長い連続を含む 12 個のデータで、zlib のストリームが参照と同じである（連続の内側の連鎖を書かないことの確かめ）。
- 200 個のデータで、CRC-32 が参照と同じである。

### 描画

- 上限の判定：固定の種の 2 万個の行列とアウトライン（値の大きさを 60 段階に変えて、桁あふれするものを含む）で、判定が「収まる」とした場合は、すべての点の `to_device` が成功し、`to_device_fitting` が同じ点を返す。「収まる」と「収まらない」がどちらも 1,000 個より多く出る。
- 上限の判定の境目：2^23 画素の前後の点で、判定が「収まる」とした場合は `to_device` が成功する。十分に内側の点では「収まる」となる。
- 交点：20 万組の線分と、その間の位置（両端を含む、i32 の端の値を含む）で、i64 の道が i128 の `div_round` と同じ値を返す。
- 塗り：小さな画像と大きな画像に 40 個ずつのランダムなパスを、二つの塗りの規則で重ねて塗り、`Canvas::fill` と、`coverage` を `Canvas::paint` した画像が同じである。
- 密な格子：[ADR 0014](0014-thread-workspaces-and-faster-check-and-fill.md) の参照との比較を、そのまま通す。
- 行列：5,000 個の行列で、単位行列との積が、計算した積と同じである。
- 割り算：5 万組の値（i64 の端の値を含む）と、1、2、3、7、72、100、1000、2^31 − 1 の整数で、`checked_div` が i128 の `div_round` と同じ値か同じエラーを返す。
- 十進の数：9 桁以下のランダムな小数 2 万個で、u64 の読み方が 2 倍の繰り返しと同じ値になる。
- 字句：10 万個の語（符号、数字、点、英字の並びと、i64 の境目の値）で、1 回の走査の字句が、`is_number` と `number` による字句と同じトークンか同じエラーを返す。
- 不透明な画素：すべての色と画素の値で、不透明度 255 の合成が色になる。

### Flate の展開と文書の読み込み

- 書き換える前の展開を、テストの中に参照の実装として残す（`src/flate/reference.rs`）。
- `tests/fixtures/flate/` のストリーム、Golem の sample.pdf のすべてのストリーム、shem の PNG の書き出しの zlib のストリームと、それらを切り詰めたものと 1 ビットを反転したもの（ストリームごとに 30 個ずつ）で、結果のバイト列、またはエラーの文が参照と同じである。
- Adler-32：300 個のデータ（長さ 0〜4 万、255 だけのものを含む）で、参照と同じ値になる。
- 演算子の使い回し：sample、figures、truetype、kanikosen（最初の 12 ページ）で、`from_pages` の `Session` で検査してから並列に描いた画像、検査せずに描いた画像、二度検査して描いた画像が、`Session::new` の画像と同じである。存在しないページの検査と描画のエラーも同じである。
- `pages_with`：内容がストリームでないページを二つ含む文書で、2、3、8 スレッドで 20 回ずつ、一つのスレッドと同じエラーを返す。sample と kanikosen で、ページが一つのスレッドと同じである。

## トレードオフ

- 上限の判定は、収まる点を「収まらない」とすることがある（境目の近く）。その場合は今と同じく一つずつ写すので、遅くなるだけで結果は変わらない。そのかわり、判定の証明（二度の丸めでそれぞれ 1 単位まで増える）を、テストで確かめ続ける必要がある。
- 参照の実装（PNG、Flate、ラスタライザ）をテストの中に持つので、テストのコードが増える。そのかわり、新しい実装が同じバイト列を出すことを、ランダムな入力で確かめられる。
- GitHub Actions の ubuntu-24.04 のランナーの 4 プロセッサは、2 コアのハイパースレッドである（`lscpu` で確かめた）。`--jobs 4` は `--jobs 2` から 1.16〜1.33 倍しか伸びず、この ADR の変更でも変わらない。
- Deflate の探索は、候補の連鎖を 128 個までたどる規則のままで、PNG の書き出しの時間の大半を占める。PNG のバイト列を変えないためである。連続の候補を式で処理する部分は、証明に頼るので、参照との比較のテストを、連続の多いデータで厚く持ち続ける必要がある。
- `Session::with_jobs`、`Session::from_pages`、`Document::pages_with` で、入り口が増える。`Session::new` の振る舞いは変えない。
- `from_pages` の `Session` は、検査から描画までの間、検査したページの演算子をメモリに持つ。kanikosen（129 ページ、内容が 3.8 MB）では、演算子が 32 万 4,842 個で、1 個 64 バイトなので約 21 MB である。描画したページの演算子は手放す。
