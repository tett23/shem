# ADR 0011: 出力のバイト列を変えない高速化（フォントの使い回しなど）

ステータス: 採択（未実装）

## 文脈

[ADR 0009](0009-render-pages-in-parallel.md) でページを並列に描くことにしたが、一つのページを描く速さは変わらない。
どこに時間がかかっているかを、Golem の `kanikosen` の fixture（縦組みの小説。[Golem の 1254092a](https://github.com/tett23/golem/tree/1254092a2ed5a7fd29bb6f1affb53806cf76c694/modules/golem-driver/test/fixtures/kanikosen) の Golem で組んだ 129 ページ、1.2 MB の PDF）で測った。
機械は Apple Silicon の macOS（10 コア）で、shem は main の 702584a を release でビルドし、一つのスレッドで 150 dpi で描いた。

| 段階 | 時間 |
|---|---|
| 全ページの検査（`check_page`、画素を描かない解釈） | 2.7 秒 |
| 全ページの描画（`render_page`） | 5.0 秒 |
| 全ページの PNG への書き出し（`encode_png`） | 8.7 秒 |
| PPM への書き出し | 0.007 秒 |
| 1 ページで使う二つのフォントの読み込み（1 回） | 0.015 秒 |

測った値から、次のことがわかる。

- **フォントの読み直し**：描画は、ページごとにフォントのプログラムを読み直している（[src/render.rs:106](https://github.com/tett23/shem/blob/702584ad2fa0137d94786b0a6b03c895af86e007/src/render.rs#L106)、[src/render.rs:132](https://github.com/tett23/shem/blob/702584ad2fa0137d94786b0a6b03c895af86e007/src/render.rs#L132)）。1 回の読み込みが 15 ミリ秒で、検査と描画で 129 ページずつ読むので、合わせておよそ 3.9 秒になる。検査の時間の大半は、この読み込みと見込む。
- **グリフの解釈の繰り返し**：同じグリフを描くたびに、charstring を解釈し直している（[src/font/cff.rs:779](https://github.com/tett23/shem/blob/702584ad2fa0137d94786b0a6b03c895af86e007/src/font/cff.rs#L779)）。この PDF で描くグリフは約 6 万 5 千個で、その多くは同じグリフの繰り返しである。
- **行のフィルタ**：PNG のフィルタの選び方は、行ごとに五つの型の結果をすべて `Vec` に作ってから比べている（[src/png.rs:226](https://github.com/tett23/shem/blob/702584ad2fa0137d94786b0a6b03c895af86e007/src/png.rs#L226)）。20 ページで 0.50 秒、1 ページあたり約 25 ミリ秒だった。
- **Deflate**：一致を 1 バイトずつ比べている（[src/png.rs:160](https://github.com/tett23/shem/blob/702584ad2fa0137d94786b0a6b03c895af86e007/src/png.rs#L160)）。20 ページで 0.82 秒、1 ページあたり約 41 ミリ秒だった。
- **ラスタライザのセル**：セルを `BTreeMap` に積んでいる（[src/raster.rs:148](https://github.com/tett23/shem/blob/702584ad2fa0137d94786b0a6b03c895af86e007/src/raster.rs#L148)）。描画から検査を引いた約 2.3 秒（1 ページあたり約 18 ミリ秒）が、主にラスタライズと合成の時間と見込む。

高速化で出力が変わると、Golem は参照の画像を作り直すことになる（[ADR 0001](0001-scope-golem-contract-and-determinism.md)）。
上に挙げた処理は、どれも同じ結果を速く出すように書き換えられる。
出力のバイト列を変えない高速化だけに限れば、既存のゴールデンがそのまま正しさの確かめになる。

## 実装すること

### 原則

- この ADR の高速化は、どれも画素と PNG と PPM のバイト列を変えない。`tests/golden/` のゴールデンを作り直さずに通すことを、各変更の条件とする。
- エラーの文言と、エラーになる入力は変えない。
- 依存は増やさない。

### フォントの使い回し

- 一つの文書を描く間、フォントを一度だけ読む。フォントのキャッシュ（`FontCache`）を、Type 0 のフォントの辞書のオブジェクトの番号を鍵として持つ。
- キャッシュは、検査（`check_page`）と描画（`render_page`）の間でも共有する。検査で読んだフォントを、描画でもそのまま使う。
- 読み込みは、そのフォントが初めて `Tf` で使われたときに行う。使わないフォントは今と同じく読まないので、資源にあるが使われないフォントの誤りでエラーになることはない。
- 読み込みのエラーもキャッシュし、同じフォントを使う別のページでも同じエラーを返す。
- 間接参照でない（資源の辞書に直接書かれた）フォントは、今と同じくページごとに読む。Golem はフォントを間接参照で書く。
- キャッシュはスレッドの間で共有できる形にする（[ADR 0009](0009-render-pages-in-parallel.md)）。鍵ごとの `OnceLock` を `Mutex` で守った表に置き、表の錠は `OnceLock` を取り出す間だけ持つ。読み込みは純粋な関数なので、どのスレッドが先に読んでも結果は同じである。
- `Font` は `Rc` から `Arc` に変える。

### グリフのアウトラインの使い回し

- `Font` の中に、グリフ ID ごとのアウトラインのキャッシュ（グリフの数の長さの `OnceLock` の並び）を持つ。アウトラインは、初めてそのグリフを描くときに解釈し、以後は同じ結果を使う。
- キャッシュするのは、グリフの空間のアウトライン（[ADR 0004](0004-glyph-outlines-cid-mapping-and-vertical-writing.md) の `Segment` の列）だけとする。装置の空間に写した点や画素はキャッシュしない。字ごとに文字の行列が違い、画素の位置も変わるからである（[ADR 0004](0004-glyph-outlines-cid-mapping-and-vertical-writing.md) で、画素の単位のグリフのキャッシュを作らないと決めた）。

### PNG の行のフィルタ

- 五つの型のそれぞれについて、フィルタ後の値を作らずに、絶対値の和だけを一度の走査で計算する。選んだ型の行だけを作る。
- 選ぶ型（和が最小、同じなら番号の小さいもの）は変えない。

### Deflate

- 一致の長さを、8 バイトずつ `u64` で比べてから、違う位置を `trailing_zeros` で求める形にする。最後の 8 バイト未満は 1 バイトずつ比べる。
- 候補をたどる順、たどる数の上限、選ぶ一致（最も長いもの、同じなら最も近いもの）は変えない。

### ラスタライザのセル

- セルを `BTreeMap` に積む代わりに、`Vec` に `(行, 列, cover, area)` を足していき、最後に `(行, 列)` で並べ替えて、同じセルの値を足し合わせる。
- 整数の和は足す順によらないので、各セルの cover と area は今と同じになる。並べ替えは安定である必要もない。

### 測定の記録

- 変更の前と後で、上の表と同じ測り方をした結果を `docs/benchmarks/` に記録として残す。記録は、機械、コアの数、shem のコミット、Golem のコミット、PDF の SHA-256、解像度、各段階の時間を含める。
- 測り方は、記録と同じディレクトリのシェルのスクリプトか、記録の中のコマンドで再現できるようにする。

### 版と文書

- 出力を変えないので、パッチバージョンを上げる（[ADR 0001](0001-scope-golem-contract-and-determinism.md)）。
- 仕様書には、振る舞いが変わらないので書き足さない。測定の記録への参照だけを仕様書の「決定性」の近くに置く。

## 実装しないこと

- 出力のバイト列を変える高速化と圧縮の改善（動的なハフマンの符号、遅延の一致、フィルタの選び方の変更など）。PNG の大きさが問題になったら、別の ADR で決める（[ADR 0007](0007-png-output-resolution-and-cli.md) の方針のまま）。
- 画素の単位のグリフのキャッシュ（グリフのビットマップの使い回し）。
- 検査と描画を一回の解釈にまとめること。書く前に全ページを検査する約束（[ADR 0002](0002-pdf-subset-and-out-of-scope-input.md)）のために、解釈は二回のままにする。フォントとグリフを使い回すので、二回目の解釈は軽くなる。
- SIMD の命令を直接使うこと、`unsafe` のコード。
- 複数の文書（複数の PDF）にまたがるキャッシュ。
- ページの中の並列化（[ADR 0009](0009-render-pages-in-parallel.md) の「実装しないこと」のまま）。

## テスト設計

### 出力が変わらないこと

- 各変更の後に、既存のゴールデン（[ADR 0001](0001-scope-golem-contract-and-determinism.md)、10 ページの PNG）を作り直さずに通す。CI の三つの環境でも通す。
- `kanikosen` の PDF を変更の前と後の shem で描き（150 dpi、PNG と PPM）、129 ページのすべてのファイルが同じバイト列であることを確かめる。PDF は大きいので fixture にはせず、確かめた結果を測定の記録に書く。

### フォントのキャッシュ

- 同じ Type 0 のフォントを使う 3 ページの PDF で、フォントの読み込みが 1 回だけであることを確かめる（テストの中だけで読み込みの回数を数える）。
- 検査の後の描画で、フォントを読み直さないことを確かめる。
- 範囲の外のフォント（`OpenType` の `FontFile3`）を 2 ページ目と 3 ページ目で使う PDF で、エラーが今と同じく 2 ページ目の一行になることを確かめる。
- 資源にあるが使われない範囲の外のフォントは、今と同じくエラーにならない。
- 間接参照でないフォントを使うページも描ける。
- 4 スレッドから同じフォントを同時に求めても、読み込みが 1 回で、すべてが同じ `Arc` を受け取る。

### グリフのキャッシュ

- 同じグリフを 100 回描くページで、charstring の解釈が 1 回だけであることを確かめる（テストの中だけで回数を数える）。
- CFF と TrueType の両方で、キャッシュから返したアウトラインが、キャッシュを通さない解釈の結果と同じである。

### 行のフィルタと Deflate

- 新しいフィルタの選び方の結果を、今の実装（テストの中に参照の実装として残す）と、ランダムに近い行、平らな行、境界の値の行（0 と 255 の交互）を含む 1000 行で比べ、型とバイト列が同じであることを確かめる。
- 新しい一致の比較で作った zlib のバイト列を、今の実装（テストの中に参照の実装として残す）と、既存の Deflate のテストのデータ、Golem の fixture の 10 ページのフィルタ後のデータで比べ、同じであることを確かめる。長さが 8 の倍数の前後（7、8、9、257、258 バイト）の一致も含める。

### ラスタライザのセル

- 既存のラスタライザのテスト（[ADR 0003](0003-paths-fill-stroke-and-antialiasing.md)）を変えずに通す。
- ランダムに作った 200 本のパス（固定の種）の覆いを、今の `BTreeMap` の実装（テストの中に参照の実装として残す）と比べ、同じであることを確かめる。

### 速さ

- 自動のテストにはしない。測定の記録で、変更の前と後を比べる。

## トレードオフ

- 出力を変えない高速化に限ったので、ゴールデンで正しさを確かめられ、Golem は参照の画像を作り直さずに済む。そのかわり、圧縮の率を上げてファイルを小さくする改善（動的なハフマンの符号など）は、この ADR に入れない。
- フォントとグリフのキャッシュでメモリーが増える。キャッシュは文書を描く間だけ持ち、グリフのアウトラインは使ったグリフの分だけ増える。Noto Serif JP のように 1 万 7 千個のグリフを持つフォントでも、使わないグリフは空の `OnceLock` だけである。
- キャッシュに `Mutex` と `OnceLock` を使うので、コードは少し込み入る。そのかわり、読み込みを先に済ませる手順（全ページの資源を集めて先に読む）を別に持たずに済み、使わないフォントを読まない今の振る舞いを保てる。
- 参照の実装をテストの中に残すので、テストのコードが増える。新しい実装が古い実装と同じ結果を出すことを、固定の入力で直接比べられる。
- 測った値は一つの機械のものである。比べたいのは同じ機械の変更の前と後なので、記録に機械を書けば足りる。
