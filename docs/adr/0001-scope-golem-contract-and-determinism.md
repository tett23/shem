# ADR 0001: 目的と版ごとの範囲、Golem との取り決め、決定性の約束

ステータス: 採択→スレッドの使用は[ADR 0009](0009-render-pages-in-parallel.md)

## 文脈

Golem（https://github.com/tett23/golem ）は、rc4 で PDF の見た目の回帰テストを入れる。
Golem が書いた PDF を画像に描き、前のコミットの画像と比べて、見た目の変化を見つける。
その画像を描くラスタライザとして、このリポジトリで shem を作る。

Golem の本体はラスタライザを要らない。
図版をフレームに合わせて拡大縮小するときも、Golem は PDF に変換の行列を書くだけで、画素を扱わないからである。
画素を扱うのは PDF を画像にするときだけなので、shem は Golem と別のリポジトリにし、Golem はテストと CI からコマンドとして呼ぶ。

shem の目的は、見た目が変わったことを見つけることである。
描いた結果が正しいことは示さない。
Golem の Writer と shem を同じ書き手が作るので、Writer の読み違いを shem も同じように読み違えるおそれがある。
実例として、PDFium が CID-keyed の CFF の文字のコードをグリフ ID として読み、和文を描かなかった件がある（[golem-pdf ADR 0011](https://github.com/tett23/golem/blob/1254092a2ed5a7fd29bb6f1affb53806cf76c694/docs/golem-pdf/adr/0011-cff-fontfile3-subtype.md)）。
この種の誤りは shem では見つからないので、正しさは外のビューアー（pdftoppm、PDFium など）で目で確かめる項目として、Golem の側に残る。

Golem の CI は、x86-64 と aarch64 で出力のバイト列を比べている。
見た目の回帰テストも同じ運用に載せるには、shem が機械によらず同じ画像を出す必要がある。
浮動小数点数の演算は、融合積和（FMA）の有無や演算の順で結果が揺れうる。

メンテナーは、版ごとの範囲を次のように決めた（2026-10-26）。
v0.1 は、今の Golem の出力に合っていればよい。
v1 では、汎用の PDF のラスタライザを目指す。
Golem の見た目の回帰テストは rc4 で入るので、まず Golem に要る分だけを早く作り、汎用にするための範囲の拡大はその後に回す。

## 実装すること

### 版ごとの範囲

- v0.1 が描くのは、今の Golem の Writer が書く PDF の部分集合である（Golem の origin/main 1254092a で調べた出力）。v0.1 では、汎用のラスタライザとしての機能を作らない。
- v0.x の間は、Golem の Writer が書くものの変化に合わせて範囲を広げる。v1 に向けた範囲の拡大も、v0.x の版で少しずつ入れる。
- v1 では、汎用の PDF のラスタライザを目指す。Golem 以外の生成系が書く PDF も描く。v1 の範囲（どの機能があれば汎用と呼ぶか）は、v1 に向けた別の ADR で決める。
- 決定性の約束（下の「決定性」）、依存を増やさない方針（下の「依存」）、範囲の外の入力でエラーで止まる原則は、v1 でも保つ。
- v0.1 の部分集合の中身（ファイルの構造、演算子、資源）は [ADR 0002](0002-pdf-subset-and-out-of-scope-input.md) で決める。
- 範囲の外の入力に出会ったら、黙って別のものを描かずに、エラーで止まる（[ADR 0002](0002-pdf-subset-and-out-of-scope-input.md)）。
- v0.1 では、画像も図版（Form XObject）も中身を描かず、灰色の箱とバツ印で表す（[ADR 0006](0006-placeholder-boxes-for-images-and-forms.md)）。

### Golem との取り決め

- Golem は shem をコマンドとして呼ぶ。golem の実行ファイルには shem をリンクしない。
- Golem は、shem のリリースのタグと、アーカイブの SHA-256 を固定して取得する（epubcheck や peg-hs と同じ扱い）。
- Golem の Writer が新しい演算子や資源を書くようになるときは、先に shem を直してリリースし、その後で Golem が固定している版を上げる。
- 同じ入力に対する画素を変える変更（描き方の変更、範囲の拡大で箱だったものを描くようになる変更など）は、マイナーバージョンを上げてリリースする（0.x の間は `0.x` の x を上げる）。リリースノートの「変更」に、画素が変わることと、変わる入力の種類を書く。
- 画素を変えない変更（範囲の外として止まっていた入力を描けるようにするだけの変更、エラーの文言の変更など）は、パッチバージョンを上げる。

### 決定性

- 同じ入力と同じオプションから、x86-64 と aarch64、Linux と macOS で、バイト単位で同じ出力を出す。
- 入力から画素までの経路で、浮動小数点数を使わない。整数と固定小数点の演算だけを使う。
  - PDF の実数と行列の要素は、符号付き 64 ビットの整数で表す Q32.32（小数部 32 ビット）の固定小数点数とする。
  - 十進の数の文字列から Q32.32 への変換は、桁の整数の演算で行い、最近接の偶数への丸めとする。
  - 掛け算は 128 ビットの整数で計算し、結果を一度だけ丸める（最近接の偶数への丸め）。行列の積の各要素は、積の和を 128 ビットで計算してから一度だけ丸める。
  - 描画の座標は、画素の 1/256 を単位とする 32 ビットの整数とする（[ADR 0003](0003-paths-fill-stroke-and-antialiasing.md)）。
- 整数の桁あふれは、検査つきの演算（`checked_*`）で見つけてエラーにする。黙って折り返さない。
- 出力に関わる処理で、`HashMap` と `HashSet` の反復の順に依存しない。順に意味があるところは `BTreeMap` か `Vec` を使う。標準の `HashMap` は、プロセスごとに乱数で鍵を選ぶからである。
- 描画はスレッドを使わずに一本で行う。
- 時刻、環境変数、ロケール、ファイルシステムの列挙の順は、出力に影響させない。

### 依存

- `[dependencies]` には何も入れない。Flate の伸長と圧縮、CFF と TrueType のアウトラインの読み取り、PNG の書き出しは、このリポジトリで書く（[ADR 0004](0004-glyph-outlines-cid-mapping-and-vertical-writing.md)、[ADR 0007](0007-png-output-resolution-and-cli.md)）。
- テストのための `[dev-dependencies]` も、最初は入れない。必要になったら ADR で決める。

### 配布

- `v` で始まるタグを push すると、GitHub Actions でビルドし、GitHub の Releases にアーカイブと `SHA256SUMS` を置く。adr-guard のリリースのワークフロー（https://github.com/tett23/adr-guard/blob/a54a2c6c3f6976f56b7614615eadce25cf84d382/.github/workflows/release.yml ）と同じ形にする。
- ターゲットは、Golem の配布物と同じ三つとする。
  - `x86_64-unknown-linux-musl`
  - `aarch64-unknown-linux-musl`
  - `aarch64-apple-darwin`
- Linux は musl で静的にリンクし、ディストリビューションを問わず動くようにする。
- アーカイブの名前は `shem-<タグ>-<ターゲット>.tar.gz` とし、`shem`、`LICENSE`、`README.md` を入れる。
- タグと `Cargo.toml` の `version` が合わなければ、リリースのワークフローを失敗させる。

## 実装しないこと

- v0.1 での、汎用のラスタライザとしての機能（今の Golem が書かないもの。xref のストリーム、単純なフォント、画像の復号、透明など）。v1 に向けた ADR で加える。
- v1 でも、ビューアーとしての操作の機能（注釈やフォームのフィールドの入力、しおり、文字の検索など）。shem はページを画像に描くだけである。
- 描いた結果の正しさの検証。正しさは外のビューアーで確かめる。
- 画像の比べ方、参照の画像の置き場所、CI の費用、意図して見た目を変えるときの受け入れ方。これらは Golem の側の ADR で決める。
- HTML の描画。
- v0.x での crates.io への公開。v1 で公開するかは、v1 に向けた ADR で決める。
- x86-64 の macOS と Windows 向けの配布物。

## テスト設計

### 決定性

- `tests/fixtures/` に、手で書いた小さな PDF と、Golem の出力の PDF を置く。Golem の出力は、生成した Golem のコミットとコマンドを `tests/fixtures/README.md` に書き、埋め込んだフォントのライセンスを確かめてから置く。
- 各 fixture の各ページを描いた PNG を `tests/golden/` に置き、`cargo test` で、描いた結果がバイト単位で一致することを確かめる。
- CI は、このテストを Linux の x86-64（`ubuntu-24.04`）、Linux の aarch64（`ubuntu-24.04-arm`）、macOS の aarch64（`macos-15`）で実行する。三つの環境で同じゴールデンに一致すれば、出力は環境によらない。
- `src/` に `f32` と `f64` が現れないことを、CI のスクリプトで確かめる（`grep -rnE '\bf(32|64)\b' src/` が何も出さない）。

### 固定小数点

- 十進の文字列から Q32.32 への変換：`0`、`1`、`-1`、`0.5`、`.5`、`-.5`、`3.`、`362.8346`、`0.00001`、小数部が 32 ビットで表せない値の丸め（偶数への丸めの境界の値を含む）、整数部が範囲を超える値（エラー）。
- 掛け算と行列の積：単位行列、平行移動、90° の回転、`[1/w 0 0 1/h 0 0]` と `[w 0 0 h x y]` の積（Golem の Form の形）の丸めの誤差の上限、桁あふれ（エラー）。

### 配布

- リリースのワークフローは、`v0.1.0-rc1` のタグで実際に動かし、三つのアーカイブと `SHA256SUMS` が置かれること、展開した `shem --version` がタグと一致することを確かめる。

## トレードオフ

- 固定小数点にすると、浮動小数点数より実装の手間が増え、桁あふれへの注意が要る。そのかわり、コンパイラーやアーキテクチャによらず結果が決まる。浮動小数点数でも FMA を止め、演算の順を固定すれば揃う見込みはあるが、標準ライブラリの関数（`sqrt` 以外の超越関数など）の実装の差まで管理するのは難しい。
- Q32.32 の整数部は ±2^31 で、ポイントの座標にも、高い解像度の画素の座標にも足りる。小数部 32 ビットは、Form の `Matrix` の `1/w` のような小さな値でも、相対の誤差を 10^-6 より小さく保つ。Q16.16 では、`w` が 500 のとき `1/w` の相対の誤差が 0.4% に達し、拡大と縮小の往復で箱の大きさが画素単位でずれる。
- v0.1 の範囲を今の Golem の出力に絞るので、Golem の rc4 に間に合わせやすい。そのかわり、v1 で汎用にするときに、読み取りの部品（ファイルの構造、内容のストリームの解釈）を広げる手間が残る。v0.1 でも、演算子の表とファイルの構造の読み取りを、範囲を広げるときに作り直さずに済む形にしておく。
- 範囲の外でエラーにすると、Golem の Writer が新しい演算子を書いた時点で、Golem の見た目のテストが止まる。黙って読み飛ばすと、新しい描画が画像に現れず、変化を見逃す。止まるほうが、見逃すより安い。
- 依存を入れないので、Flate やフォントの読み取りの誤りは自分で直すことになる。そのかわり、依存の版の更新で画素が変わることがない。
