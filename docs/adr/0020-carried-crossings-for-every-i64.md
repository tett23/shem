# ADR 0020: 交点の商と余りの持ち越しを、i64 のどの入力でも正しくする

ステータス: 採択

## 文脈

[ADR 0019](0019-faster-deflate-sweep-and-operands.md) は、線分が横切る行と列の交点を、最初の交点だけを割り、次からは商と余りを持ち越して求める形にした（`interpolations`、[src/raster.rs:255](https://github.com/tett23/shem/blob/02891de66521b1caf32a4cbdcef53838c9c735da/src/raster.rs#L255)）。
そのとき、次の検査を入れた。

> 積が収まるかは、線分ごとに `db · d` で一度だけ確かめる（どの交点も |at − a0| < d）。収まらなければ、今と同じく交点ごとに `interpolate` を使う。

実装の後、Fable のエージェントにテストを検査させた（2026-11-08、[PR #36](https://github.com/tett23/shem/pull/36)）。
その報告で、二つのことがわかった。

一つ目に、今の呼び出しでは、この検査は落ちない。
検査を `let fits = true;` に変えても、テストはすべて通った。
積が i64 を超える線分（端点が i32 の両端のもの）を描くテストも含めて、である。

二つ目に、[ADR 0019](0019-faster-deflate-sweep-and-operands.md) の理由づけは、持ち越す形に合っていない。
`db · d` は、交点ごとに割る形（`interpolate`）が、最後の交点で計算する積の上限である。
持ち越す形が計算する積は、最初の交点の積と、間隔の積の二つだけである。
`crossings(a0, a1)` は a0 と a1 の間の 256 の倍数を a0 の側から並べるので、最初の交点は a0 から 256 以内（0 < |at − a0| ≤ 256）にあり、間隔は 256 である。
どちらの積も 256 |db| 以下で、`db · d` よりずっと小さい。

今の二つの呼び出し（`render_line` と `render_row_piece`）では、a と b は i32 の範囲にある。
そのため、|db| と d は 2^32 − 1 以下で、持ち越す形の計算はどれも i64 に収まる。

しかし、i32 の範囲に頼ると、`interpolations` は引数の型（i64）が示すより狭い範囲でしか正しくない。
今の `fits` の検査は、その前提が崩れたときにも正しい値を返すための道だが、条件が持ち越す形に合っていない。
条件は、二つの向きで外れている。

- 厳しすぎる：|db| = 2^40、d = 2^30 では `db · d` が 2^70 で「収まらない」となるが、持ち越す形の積は 2^48 以下で収まる。今の呼び出しでも、端点が i32 の両端の線分は、この理由で交点ごとに割る道に回る。
- 足りない：`a1 − a0` と `b1 − b0` の引き算そのものが、i64 の端の値（a0 = i64::MIN、a1 = i64::MAX など）であふれる。また、|db| = 1、d = 2^62 + 256 では `db · d` は収まるが、持ち越す形の余りの和 r + dr（2d より小さい）は 2^63 を超えうる。

i64 のどの入力でも正しい値を返す形を試した。
すべてを i128 で持ち越すと、kanikosen の 300 dpi の PPM の `--jobs 1` のユーザー時間が、0.62 秒から 0.74 秒に増えた（手元の Mac、5 回ずつ交互に走らせた中央値。値は 0.62、0.62、0.62、0.63、0.65 と 0.74、0.74、0.74、0.75、0.78）。
交点の足し算は描画のいちばん内側のループにあるので、i128 の足し算と比較の分が効く。
出力のバイト列は同じだった。

## 実装すること

### 二つの道

`interpolations` を、i64 のどの a0、a1、b0、b1 と、`crossings(a0, a1)` の交点でも、交点ごとに i128 で割って丸めた値（`b0 + div_round((b1 − b0)(at − a0), a1 − a0)`）と同じ値を返す形にする。
線分ごとに一度だけ、次の条件を確かめる。

- `b1 − b0` と `a1 − a0` が i64 で計算でき（`checked_sub`）、正の除数に正規化した後で |db| ≤ 2^54、d ≤ 2^61 である。

この条件が成り立てば、i64 で持ち越す。
成り立たなければ、i128 で持ち越す。
どちらの道も、最初の交点の積と間隔の積を割り、その後は商と余りを足して一度だけ繰り上げる、同じ手順である。

i64 の道の値は、次の範囲に収まる。

| 値 | 範囲 |
|---|---|
| 最初の交点の積、間隔の積 | 絶対値が 256 · 2^54 = 2^62 以下 |
| 商 q | どの交点も a0 と a1 の間にあるので、絶対値が \|db\| ≤ 2^54 以下 |
| 余り r、r + dr | 0 以上 2d ≤ 2^62 より小さい |
| b0 + q + 1 | 丸めた値は b0 と b1 の間にあるので、i64 に収まる |

i128 の道では、i64 の値の差は 2^64 より小さく、積は 2^72 より小さいので、どれも i128 に収まる。
丸めた値は b0 と b1 の間にあるので、i64 に戻せる。

### 書き方

- 持ち越しの手順は、i64 と i128 の両方で使う一つの関数にする。型の違いは、ユークリッドの商と余り（`div_euclid`、`rem_euclid`）を持つ小さな trait で吸収し、i64 と i128 に実装する。
- `fits` の検査と、`interpolate` に回す道を外す。
- `interpolate` は、ライブラリのコードから使われなくなるので、テストの比較の相手として `#[cfg(test)]` にする。参照の実装（`src/raster/reference.rs`）の `interpolate` はそのまま残す。
- `interpolations` の文書のコメントに、二つの道の条件と、上の表の上限を書く。

### 文書

- 仕様の決定性の節の「線分と行や列との交点は、積が i64 に収まれば、最初の交点だけを割り、次からは商と余りを持ち越す」を、この ADR に合わせて書き直す。
- [ADR 0019](0019-faster-deflate-sweep-and-operands.md) のステータスを「採択→交点の積の検査はADR 0020」にする。

## 実装しないこと

- i128 の一つの道にすること。上の試作のとおり、300 dpi の描画が約 2 割遅くなる。
- 交点の計算のほかの変更。今の呼び出しでは、i64 の道を通り、値と丸めは今と同じなので、出力のバイト列は変わらない。
- `render_line` と `render_row_piece` の座標の型を i64 に広げること。点は今と同じく i32 の組（`Point`）である。この ADR は `interpolations` だけを、引数の型の範囲で正しくする。

## テスト設計

### 参照

- テストの中に、交点ごとに i128 で割って丸める参照（`b0 + div_round((b1 − b0)(at − a0), a1 − a0)` を i128 で計算する）を置く。`interpolate` は a1 − a0 や b1 − b0 が i64 であふれる入力を扱えないので、i64 の全範囲の比較には使わない。

### i64 の全範囲

- 20 万組の線分：a0 を i64 の全範囲（i64::MIN、i64::MAX、0、±1、±2^31、±2^54、±2^61 の近くを含む）から選び、a1 を a0 から ±40 · 256 以内（i64 の範囲に収める）にする。b0 と b1 は i64 の全範囲から選び、2^54 と 2^61 の境目の前後、i64::MIN と i64::MAX の組を含む。`interpolations` が参照と同じ値を返す。
- 二つの道の境目：|db| が 2^54 − 1、2^54、2^54 + 1、d が 2^61 − 1、2^61、2^61 + 1 の線分で、どちらの道を通っても参照と同じ値を返す。この線分で道が実際に分かれることを、テストのための関数（`#[cfg(test)]` で道の名前を返すもの）で確かめる。
- 方向と交点の数：a0 < a1 と a0 > a1、交点が 0、1、2、40 個のもの。丸めの同点（余りが除数のちょうど半分）になる線分を含む。

### 今の呼び出し

- 既存のテストを、そのまま通す：`carried_crossings_equal_the_divided_ones`、`a_segment_whose_products_pass_i64_is_divided_at_each_row`、ゴールデン、kanikosen のバイト列の一覧。
- 端点の組み合わせ：x と y のそれぞれを i32::MIN、i32::MIN + 1、−1、0、1、i32::MAX − 1、i32::MAX から選んだ線分（y が違うもの）を、`render_line` で描いたセルが、行ごとに割る形（[PR #36](https://github.com/tett23/shem/pull/36) のテストの `render_line_divided`）と同じである。i32 の全範囲を横切る線分は、行を間引いて比べる。

### 確かめ方

- i64 の全範囲のテストは、今のコードでは失敗する（`interpolate` の道が、a1 − a0 や b1 − b0 であふれる）ことを、実装の前に確かめる。
- 実装の後、fixture の五つの PDF を 72、150、300 dpi の PPM で描き、main と同じバイト列であることを確かめる。kanikosen の 300 dpi の PPM の `--jobs 1` の時間が、main と変わらないことも確かめる。

## トレードオフ

- 二つの道を、一つの関数と小さな trait で書くので、コードは今より少し抽象的になる。そのかわり、手順は一つで、どちらの道も同じテストで確かめられる。
- 今の呼び出しは、i128 の道を通らない。i128 の道は、i64 の全範囲のテストだけが通る。将来の呼び出しで i32 の範囲を超える座標を使うときのための道である。
- 条件の確かめは線分ごとに一度だけなので、速さはほとんど変わらない見込みである。実装の後に測って確かめる。
